# ML 子系统：离线批处理，JSON 产物经 biz-core 内部接口入库

## 背景
五部分全部必做，ML 完整做但必须与主系统解耦（Opt-in）。周期仅 10 天，验收 9/11。ADR-0001 规定 biz-core 是唯一写库者，ML 进程同样不得直连业务库。

## 决定
- 形态：ml/ 独立 Python 目录（pandas + LightGBM，基线 Holt-Winters 对照），不进 CMake，Qt 主工程零依赖
- 输入：biz-core 提供的 HTTP 只读导出端点（token 鉴权）返回历史充电记录 CSV（时间/站ID/桩ID/电量/时段/星期/节假日/天气特征），历史数据由造数脚本批量生成 30~60 天模拟记录
- 模型：站×小时聚合 + 外生变量回归（LightGBM 可直接消费节假日/天气特征）；不引入深度学习
- 输出：out/predictions.json（含 forecast_at、model_version、每站 1h/6h/24h 的 load 并发桩数与 free_piles）→ POST biz-core 内部端点 /api/internal/ml/ingest（本地 token）→ biz-core 校验后**整批**写 t_ml_prediction（ML 进程零 SQL）
- 消费方：dashboard 负荷预测曲线；user-app station.list 的 pred_free 推荐排序开关；ops-app warning.list 的 kind=3 负荷预警行
- 触发：定时重跑（默认现实每 2 分钟一次，配合加速因子≈模拟时间一天，形成准实时刷新；亦可手动触发），不在请求路径上

## 理由
- 契约（导出端点 in → predictions.json → ingest out）冻结后模型可独立替换升级，符合"解耦、Opt-in"要求
- ML 不触库维持唯一写者边界（ADR-0001），校验失败整批拒绝不部分入库
- 不拖累关键路径（biz-core 协议/状态机）

## 后果
- biz-core 需实现导出端点 + ingest 端点 + t_ml_prediction 表（含 forecast_at/model_version/mape 字段）
- 演示前需预跑一次批处理保证大屏有预测数据
