# 常驻服务端进程作为唯一数据权威（biz-core）

## 背景
充电桩平台包含用户端(user-app)、后台管理端(ops-app)、Web大屏(dashboard)、模拟电桩(simulator)、ML(ml) 多个消费方，需要数据一致性和"预约-充电-计费-结算"状态机的中立裁判。曾考虑：a) 用户端↔后台点对点；b) 各进程直读共享 SQLite 文件。

## 决定
建一个常驻 QT 服务端进程 **biz-core**，作为唯一数据权威：
- 唯一持有数据库写权，其他进程一律不直连业务库
- **对外 RESTful HTTP + JSON**（user-app / ops-app / dashboard），token 鉴权；大屏经快照接口取数，不触库
- **对内 TCP Socket**（biz-core ↔ simulator）：自定义帧（4B 长度+JSON），指令/上报/心跳语义——命中说明书"Socket 通信编程"考核点（1.2/1.6）
- 内部多线程：HTTP 线程池 + socket IO + 业务队列（单写者）；业务状态以不可变快照发布，读路径无共享可变状态

## 理由
- 点对点方案下后台非常驻，管理员离线即服务中断，且状态机无中立裁决方
- 共享文件直读在多进程并发写下有锁冲突，且绕开 socket 考核点
- 订单状态机、远程重启指令下发、大屏供数、ML 结果入库天然有统一落点
- RESTful 作为对外标准（可 curl 调试、语义清晰、Qt 原生支持）；裸 socket 仅保留在最能体现"设备管控"语义的 simulator 链路，兼顾考核

## 后果
- biz-core 是关键路径，协议 v1 必须最早冻结（D2）
- 各客户端依赖协议定义（common/），协议变更需同步
- REST 无服务端推送：用户端充电进度用 2s 轮询（演示可接受）
