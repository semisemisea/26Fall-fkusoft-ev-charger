# 数据模型草案（非冻结——biz-core 内部设计参考）

> **文档定位（必读）**：本文件**不是冻结设计，不是 DDL，也不进评审冻结范围**。它存在的唯一目的：证明协议 v1 里的每条 API 在数据层面是可实现、无歧义的。实现期 biz-core（A 线）可随时修改本文，不需评审其他线；其他四条线只依赖协议，不依赖本文。评审 Agent 注意：此处任何内容都不构成对客户端的约束。

## 为什么有这份文档（给评审 Agent 的背景）

- 所有端经 biz-core 访问数据，客户端永不写 SQL → 对外契约只有协议 v1
- 但 API 字段语义来自数据关系（"所属电站"是 sid 还是名称？累计时长什么单位？），不先理清数据关系，API 设计就是在猜测存储
- 前两轮评审的真问题（station.create 建不出桩、settle_by 无法区分角色、并发预约靠什么保证先到先得）全部是数据模型问题——本文就是把这类问题在写码前暴露
- 结论：协议 v1 = 对外合同（冻结）；本文 = biz-core 施工草图（演进），"正确 API 的可实现性证明"

## 模型约束（自然语言规范，非 SQL）

### 实体与标识

1. **用户**：11 位手机号全局唯一，是登录与注册键；uid 代理主键。余额整数分、非负。状态仅 正常/冻结 两值。
2. **管理员**：用户名唯一；初始化时种子数据 admin/123456。
3. **充电站**：名称、地址、经纬度、电价（分/度，正数）。由管理员创建，是桩的属主。
4. **电桩**：属于唯一充电站；**业务编号 code 全局唯一**（管理员可读可自定，如 K01/M02），pid 为内部主键——simulator 认领桩、UI 展示桩均用 code。类型仅 快/慢 两值；功率正数；状态五值：空闲/预约锁/充电中/故障/离线。累计次数与累计时长为**单调累加字段**（充电结算时更新），非实时聚合。
5. **订单**：属于唯一用户+唯一桩+唯一站；状态机六值见 module-design（预约中/充电中/待结算/已结算/已取消/已超时），另有异常第七态 Failed（仅内部兜底写库失败产生，协议 §2.5）。记录预约/开始/结束时间、目标电量（可空=不限）、实际电量（非负）、金额（分，非负）、结算时间与**结算者（类型+ID 两字段区分用户/管理员，同值 ID 不混淆）**。

### 关键不变量（服务端事务内保证，API 正确性的根据）

6. **单活动订单**：任一用户同时至多一个 预约中/充电中/待结算 订单——数据库层唯一性约束兜底（部分唯一索引），不靠应用层"先查后写"。这是 pile.reserve 原子拦截（2004）和"并发预约先到先得"的实现根据。
7. **桩状态与订单状态同事务变更**：预约锁桩成功 = 桩状态原子翻转 + 订单创建在同一事务；不存在"桩空但订单锁不到"或反之的中间态。
8. **余额不变量**：余额 ≥ 0 恒成立（含充电中取消折算）；每次余额变动必伴随一条流水（充值/结算扣款/取消折算扣款三种类别），订单、流水、余额三方在单事务内一致。
9. **唯一写者**：全系统仅 biz-core 进程写库（含 ML 预测结果，经 ingest 端点校验后由 biz-core 代写）；ML 进程、客户端、simulator 零 SQL。

### ML 预测数据

10. **预测记录**：站 × 时间范围（1/6/24h）一行；负荷口径 = 该站预测并发充电桩数；附带预测目标时点、批跑时间、模型版本、回测误差（可空）、**peak_hours 高峰充电时段（start/end，模拟时钟 HH:MM——说明书 ML 章节要求，契约见协议 §1.4）**。由 ingest 端点**整批替换**同轮次数据，无部分写入。消费方：大屏曲线与高峰时段 / user-app 站列表 pred_free / ops 预警列表。

### 告警

11. **告警记录**：四类（桩故障/心跳超时离线/待结算超时/负荷预警），引用桩或订单 ID，含恢复时间（空=未恢复）；大屏与 ops 预警页共用。

### 演示数据约定（E 线交付，随实现可调）

12. 种子：admin + 4 个演示账号（正常/待结算/低余额/已冻结，昵称按"用户+手机号后4位"缺省规则）；3~5 站、每站 4~8 桩（code 唯一）；区域坐标表供 user-app mock。
13. 历史生成器：30~60 天订单，含 时段分布/星期/节假日/模拟天气 特征列，供 ML 训练与大屏历史曲线。

## 实现提示（非约束）

- SQLite WAL 模式；PRAGMA foreign_keys=ON 每连接开启；金额/时间分别用整数分、unix 秒存储
- 预约/结算/状态迁移/ingest 四类操作必须单事务完成（清单见前两版 DRAFT-2，实现时照搬）
- 索引按查询路径加（活动订单唯一索引、桩(站,状态)、订单(状态)/(站)、流水(用户)、告警(未恢复)、预测(站,范围)），实现期用 EXPLAIN 校准，本文不锁定
